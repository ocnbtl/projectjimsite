# Cloudflare Free feasibility: MCC owner dashboard

Date: October 9, 2026. Decision: keep Free as the target, but do not approve the current backend unchanged for production on its published 10 ms CPU budget.

## Live evidence

The isolated `mcc-free-plan-probe` Worker ran on Workers Free using the dedicated synthetic D1 database `mcc-free-plan-test` (78ab3260-f9eb-401a-ae46-dcaa28b7967c). It used the actual application backend and actual Better Auth password functions. No real customer data, real emails, R2 files, public-site routes, or other projects were involved.

- Final benchmark batch: 27/27 checks passed (two controls, five password hashes, ten correct-password checks including five concurrent requests, five incorrect-password rejections, five 200-row CSV parses).
- Full backend sequence: 23/23 expected HTTP outcomes passed. Includes owner/crew setup and login, Secure/HttpOnly cookie assertion, unauthorized rejection, disabled public signup, customers/jobs/assignments, owner-only field exclusion from crew responses, forbidden crew financial export, expense and mileage records, 200-row expense import preview/commit, owner export, signout and session invalidation.
- This is a bounded synthetic functional test, not a comprehensive security audit or sustained load test.
- Initial hostname/secret propagation produced temporary 404s. The final batch waited for propagation and passed. These initial 404s were not CPU-limit failures.

## Actual Cloudflare CPU measurements

Selected request logs, not local stopwatch estimates:

| Operation | CPU time | Wall time |
| --- | ---: | ---: |
| Password hash | 69 ms | 69 ms |
| Crew email/password sign-in | 75 ms | 332 ms |
| Save one expense | 8 ms | 271 ms |
| Preview 200 expense rows | 136 ms | 5,224 ms |
| Commit 200 expense rows | 146 ms | 5,295 ms |

Metrics snapshot across 80 then-ingested invocations: median CPU 61.15 ms, p90 87.43 ms, p99 146 ms; zero CPU-limit errors; memory p99 34.57 MB. Observability had 92 successful invocation events by the next read, reflecting dashboard ingestion lag and additional control/denial calls. These totals are not the test assertion count.

Worker full-workflow version: `a1907181` (dashboard prefix). Primitive hash sample version: `49fa1c56-cd8c-4ccc-b2c2-eaa4d9bdb803`.

Screenshot: `cloudflare-metrics-2026-10-09.png`.

Cloudflare documents a Free limit of 10 ms CPU per request and flexibility for infrequent overages. Success above that limit cannot establish reliable production fit. Wall time spent awaiting D1 is different from CPU, but the measured import CPU itself also exceeded the budget. The issue is not simply visitor count or total records.

## Recommended zero-subscription path

1. Replace application-side password hashing with a suitable managed login, such as Cloudflare Access one-time email PIN. Verify available Free seats and validate Access identity on every private backend request; preserve owner/crew authorization. This changes the requested password experience and requires user agreement before implementation. Do not weaken password hashing to meet a hosting limit.
2. Refactor imports into bounded resumable batches, reduce repeated database work, and retest CPU per batch with realistic payloads. Batch size remains unproven.
3. Recheck normal endpoint CPU, including cold starts and larger datasets, after these changes. One 8 ms expense write is encouraging but has limited headroom and is not a guarantee for every operation.
4. Verify private receipt uploads separately, compress images, and apply storage controls. Existing account R2 is a metered subscription with a free allowance, not a guaranteed hard $0 cap. Other projects share allowances. No R2 uploads or paid plan changes were made for this test.

D1 Free includes 5 million rows read/day, 100,000 rows written/day, and 5 GB account-total storage. Workers Free includes 100,000 requests/day. These appear ample for a small crew, but actual account-wide usage, indexes and data growth must be measured. This is a forecast, not demonstrated long-term capacity.

Not validated: receipt/OCR processing, live QuickBooks or Invoice Simple integration, production owner onboarding/recovery, sustained concurrency, complete browser workflows, and long-term reliability. CSV import was tested, not accounting-provider synchronization.

## Cleanup and remaining artifacts

The test Worker has `workers_dev: false`, preview URLs disabled, and expiration set to zero. Cleanup deployment `e512f7dc-7319-43c4-af0e-95294cebf15c` reported no targets deployed. An external POST to the test endpoint returned 404 afterward. No domains/routes were assigned. The tiny synthetic test database and Worker definition remain for reproducibility; no real records are stored. The public MCC site and other Cloudflare projects were unchanged.

Rerunning requires explicit authorization, re-enabling only this test endpoint, and a fresh synthetic database for `--full` because bootstrap is intentionally single-use. The harness accepts `--live` as an explicit opt-in. Do not use production credentials or data. Application typecheck and test-runner syntax check passed after the investigation.
